# Agent tools

Every tool Octant itself gives an AI agent, with what it does, where it is
offered, and how its authority works. This page is a lookup, like
[Host reads and commands](host-reads-and-commands.md): each rule here is stated
by the specification it links to, and where the two differ, the owner wins.
Provider-native tools (a runtime's own shell, file edits, or subagents) and
tools from plugins or MCP servers the person added are not listed.

## How tools reach a model

- **Transport.** Each runtime receives the same definitions through the channel
  its adapter verified: Claude Code through Octant's in-process MCP server,
  Codex as dynamic tools when a thread starts, OpenCode and ACP agents through
  a private bridge, Pi through Octant's extension, and Octant Harness and model
  endpoints in the request itself. See
  [Architecture: Process topology](../architecture.md#process-topology).
- **Availability.** Only a provider that carries app-managed tools receives
  them: `capabilities.appManagedTools` is supported, or the model is verified
  for tools. A family whose grant or capability is off is omitted rather than
  offered and refused, decided per session where the runtime keeps its own
  tool list. A Claude Code session keeps listing a tool from the first turn
  that offers it, and the host refuses it in a turn that does not; a Codex
  thread keeps the tools it started with. A family whose operations differ by
  turn lists only the ones this turn may use.
- **What tells the model about them.** Each tool's description, and a `help`
  operation on the capability families. Octant's instructions add one line per
  offered first-party tool saying when to reach for it, from one source
  (`appToolHostLines` in `apps/server/src/providers/appToolHostLines.ts`) that
  every runtime reads: Claude Code, Codex (its `/review` turns included), OpenCode
  and ACP agents, Pi, Octant Harness, and child runs, which get the lines for
  the tools they are offered. A line says when, not how, and promises no
  approval that differs by access level; it is sent only while its tool is
  offered, its text does not change with the tool's operations (a
  coordinator's `octant_threads` has its own line), and lines are sorted by
  tool name so the cached prefix survives. Octant Harness describes each tool
  once: its guide (`nativeHarnessToolGuide`) adds only the lines a turn did not
  already carry, and its own `diagnostics` and `skill`. The Canvas delivery
  rule stays separate and is sent when Canvas is offered. Plugin and MCP tools
  get no line. A test fails when a first-party tool has neither a line nor a
  stated reason to go without one.
- **Authority.** No definition and no instruction grants anything. The host
  decides each call: Plan mode, the thread's access level, per-act approval,
  the thread's tool constraints, and outside-content taint. See
  [Architecture: Security and authority](../architecture.md#security-and-authority)
  and [Tool calls in Chat and Work](../architecture.md#tool-calls-in-chat-and-work).

- **Size.** What Octant itself gives each runtime, its instructions and tool
  definitions in the first prompt and what it sends again on each later turn, is
  measured by `bun run prompt-size:check` for the widest lead and child-run turn
  of each mode, from the real definitions and each adapter's own encoding, with
  no server. `scripts/agent-prompt-size-budget.json` holds the exact sizes with
  no headroom, and CI fails when one grows past it, so a tool offered somewhere
  new raises the budget visibly, by what it needs. The person's own skills,
  memory, files, plugins and MCP servers, and a runtime's own prompt, are not
  counted. The tool lists are upper bounds per context, kept with this page.

## Child runs

A child run started through `octant_agents` inherits its parent's tools by
default (maintainer decision, 2026-11-17), each built again from the child's own
run: its recorded workspace (its own worktree in Code, the Project's folder in
Work, none in Chat), its clamped grant, and the model it runs on. It is never
handed its parent's tool set, window or authority, and it never acts as its
parent: what it starts, reads and is marked by is kept under its run, and only
its asks appear on the parent's thread.

- **A child never exceeds its parent.** A tool is offered only when the
  child's grant holds tools, its own launch proved it carries them, the parent
  thread's provider carries them too, and the parent's profile allows the tool.
  Each call is judged again against the child's own run, the parent's live
  grant (a parent turn narrowed to Plan leaves a wider child nothing), the
  parent's tools, and the Project; a call that fails is refused.
- **Same approvals.** Plan, the access level, per-act approval, the profile's
  tool constraints and outside-content marks apply as for the lead, at the
  child's own level. A child's ask is single-use on the parent's thread: no
  remembered answer of the parent's settles it and none is kept. A child's own
  marks and its parent's both count where the lead's would.
- **Someone must be able to answer.** A tool that may ask is withheld from a
  child of a routine's run or another host-started turn, from a child whose
  window is gone, and from a child in Plan. Chat children run read-only, so
  they get only reads.
- **Nothing a child starts outlives it.** Terminals, debug sessions, language
  servers it started, Simulators and emulators it booted, recordings and
  Computer grants stop when its run ends or is cancelled, and at once when it
  no longer holds its grant. Devices a child booted are listed on disk and shut
  down when the host next starts; terminals, debug sessions and language
  servers are already reaped then.

## Withheld on purpose

- OpenCode carries Octant's tools in Chat only when its launch proves it is
  exclusive; its "mixed" rating applies at Full access, which Chat has no level
  for (maintainer decision, 2026-11-17).
- Work in a server Project runs only on Octant Harness
  ([Server Projects](server-projects.md)).
- A routine's run has no `octant_agents` ask path and no page scripts: nobody
  can answer them.
- Bots get no tools; bots are not built.
- A runtime that cannot prove it carries the tools gets none: OpenCode without
  its exclusivity proof, an ACP agent without HTTP MCP, Pi below its verified
  release, and OpenCode and ACP on Windows, where the bridge is not built
  ([Provider runtimes](provider-runtimes.md); maintainer decision, 2026-11-17).

"Code + tools" below means a Code thread on a provider that carries
app-managed tools, subject to the thread profile's tool constraints.

## Octant Harness tools

Model endpoints run through Octant Harness, which supplies its own core tools.
Plan mode drops every tool whose approval class it refuses.

| Tool                                           | Modes                                              | Authority                                                                                                                                                                        |
| ---------------------------------------------- | -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `read`, `grep`, `glob`                         | Work, Code                                         | Project file reads; no approval                                                                                                                                                  |
| `edit`, `write`                                | Work, Code                                         | Project file writes; ask per the thread's level; `edit` needs a prior read of the file                                                                                           |
| `bash`                                         | Work, Code                                         | Shell commands at the thread's level                                                                                                                                             |
| `web-fetch`, `web-search`                      | All; Chat only while research is on                | Network access; mark the thread as having read outside content; `web-search` is the one Chat search (above), and refuses a tainted thread's data-bearing query below Full access |

## ACP client bridge

An ACP agent in Code reaches files and terminals through Octant's client
capabilities rather than model-visible tools: `octant_acp_fs_read_text_file`,
`octant_acp_fs_write_text_file`, and `octant_acp_terminal_create`, `_output`,
`_wait_for_exit`, `_kill`, and `_release`. Paths stay inside the checkout and
its extra folders, under the secret guard; Plan offers only reads; at most
eight terminals live at once, each for at most ten minutes. See
[Provider runtimes](provider-runtimes.md).
