# Canvas HTML frames threat model

- Date: 2026-10-13
- Threat model id: `canvas-html-frames-v1`
- Status: Accepted with
  [Canvas documents, designs, and prototypes](../architecture.md#canvas-documents-designs-and-prototypes).
  Static frames that run nothing ship today under
  [0164](../decisions/0164-canvas-designs-are-html-in-a-frame-that-runs-nothing.md),
  measured and themed static frames (F2) ship with Canvas schema version 16,
  asset-bearing static frames (F5) with version 17, and running frames with
  version 18, with F1, F3, F4, F6, F7, F8, F9, and F10 implemented and tested.
  Pages a person imports (F15) ship under the same tiers with no schema
  change.
- Scope: agent-authored HTML, CSS, and script drawn in a Canvas `design`
  frame, and HTML pages a person imports into one, in the sidebar, the
  thread, preview, authenticated snapshots, and HTML export

## What the frame can hold

A frame holds what its author wrote, plus assets the server resolved for it
under the thread's authority. The author is the agent working for this
person, which already has that content and its own tools. The boundary
therefore protects Octant and the person from the frame, not the frame's own
content from its author: a frame must gain nothing the agent did not already
have, must not reach anything beyond its own bytes, and must not cost the
person their app.

A frame can also hold a page a person imported (F15). Its author is whoever
made the file, not the person's agent, so the frame's own content is outside
content. The boundary is the same one: an imported page is held to the same
tiers, markup policy, and limits as an agent's design, and gains nothing an
agent-authored frame does not.

## Assets

- Octant renderer origin: cookies, storage, DOM, RPC, preload, host tokens
- Project files and artifacts beyond the assets a frame names
- Loopback services and the network from the person's machine
- Renderer responsiveness (hang, memory, GPU)
- The person's trust in what is Octant chrome and what is a frame
- Snapshot viewers and export recipients

## Explicit non-goals

- Typed catalog blocks, including `tabs`, `columns`, diagram styles, Gantt,
  and Mermaid import; they render first-party components and no markup
- Public share links, whose frames are drawn from a separate user-content
  origin under the rules in
  [Canvas public links](../design/canvas-public-links.md#viewer-safety)
- A frame that runs script with `allow-same-origin`; no tier admits it
- Protecting frame content from the agent that wrote it

## Frame tiers

| Tier                        | Document                                          | Sandbox                                                                                                                                              | Policy                                                                                                                                                                                                             |
| --------------------------- | ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Static (0164)               | `srcdoc`                                          | empty                                                                                                                                                | Frame policy below, narrowing the inherited app policy                                                                                                                                                             |
| Static, measured and themed | `srcdoc`                                          | `allow-same-origin` only                                                                                                                             | Same; no script can run, so same origin grants the page nothing it can use                                                                                                                                         |
| Running                     | Served by the host route with a single-use ticket | `allow-scripts` only, in the response's `sandbox` directive, and in the parent frame in a browser; on desktop a surface of its own with no route out | `default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data: blob:; font-src data:; media-src data: blob:; connect-src 'none'; frame-src 'none'; form-action 'none'; base-uri 'none'` |

The static frame policy is today's: `default-src 'none'; style-src
'unsafe-inline'; img-src data:; font-src data:; base-uri 'none';
form-action 'none'`. The app policy's `frame-src` admits `'self'` and the
loopback design-page path (the packaged `file://` and Vite renderers reach the
loopback host); the remote gateway's document policy narrows a remote
client's `frame-src` to that path on its own origin.

## Residual risk

- WebRTC is outside a page's content policy. Desktop contains it by giving a
  running prototype a process with no route out and no resolver (F3); a remote browser and an
  exported file do not, and there a peer connection that names a TURN server
  over TCP connects (on Electron 43.5.0, one connection to a local listener,
  with the renderer's UDP policy set). What a prototype could send is what it
  holds, which its author already had. The agent's preview browser has its own
  no-route configuration (F14).
- A desktop prototype is drawn as pixels from the prototype host, so text
  typed through an input method's composition does not reach it, and
  assistive technology cannot read inside it; the canvas carries the
  prototype's name. Accepted by the maintainer on 2026-10-16 as the cost of
  the prototype host.
- The prototype host was measured on macOS only (Electron 43.7.11), with
  input delivered through Electron's input API rather than by the operating
  system. The containment probe opens a phone prototype in the host through
  the main process's surface code and clicks it there: clicks landed on the
  target and the decoy at the page's own coordinates (260, 660 and 50, 50),
  and the frames the host sent drew the page's own colours at those points.
  The renderer's canvas, outside the app, painted a host frame scaled to half
  size and turned a click on it into the page's own coordinates (a click 30,
  40 into the half-size canvas reached the page at 60, 80). In an unsigned
  packaged app (2026-10-16), the window's own bridge prepared the surface: the
  app started the host from its own executable with the host switch, the
  host's network process carried the not-found resolver rule, and the host
  read back its closed network before it said it was ready. Reloading that
  window stopped the host, and quitting the app left no host process. The
  containment probe also passed with that packaged app's host
  (`OCTANT_PROBE_PACKAGED_APP`): no UDP, TCP, HTTP, host route, or name lookup.
  Not measured: a prototype opened and driven from a Canvas in the running app,
  unpackaged or packaged and signed; the in-thread placement of a prototype;
  real operating-system keyboard and pointer input.
- A running frame in a remote browser is also not contained against a
  self-navigation to a page that runs its own script and makes its own
  requests (F7). What it can send is bounded by what the frame holds, which
  its author already had; the Run control says so.
- A tab hang in a remote browser that does not isolate sandboxed frames
  (F6): Playwright's old-headless Chromium shell hung the parent on a frame's
  infinite loop. Chrome for Testing kept the parent running, but kept the
  looping page's process for the next frame from the same host, so a
  prototype run again in that tab, even after a reload, did not load; a new
  tab did. The stopped message in a browser says to open a new tab.
- In a browser, before the person tabs or clicks into it, a running page can
  still take focus by script in some cases (observed on Electron 43 from a blur
  handler). On desktop the page never holds the window's focus (F10).
- Chromium once stopped painting sandboxed frames that were `inert` or had
  `pointer-events: none` (0164). Every tier keeps frames hit-testable and
  covers a still frame instead.
- The secret filter cannot read markup. Shared and exported frames rely on
  the person's acknowledgement, not on scanning.
- An exported file is opened in the recipient's own browser. Its prototype
  cannot make a request or load another page (F11), but WebRTC is outside a
  page's policy and is not contained there, as in a remote browser (F3). What
  it could send is what the frame holds, which its author already had.
- A themed design is exported with token values the person's window hands
  over. They are written into a sandboxed frame's stylesheet after two checks
  (the contract's and the host's), only under names a frame receives, so a
  value cannot end its rule or name something to load, and the frame could
  load nothing if one did.
- Content inside a frame is the author's. A frame can look persuasive; F8
  keeps it from looking like Octant.
- An imported running page is written by whoever made the file. On desktop
  it is contained like any prototype (F3). In a remote browser, as for any
  running frame, its script can reach the network by WebRTC or by navigating
  itself (F3, F7), so the file's author can learn that it was opened and the
  browser's address; what it can send is what it holds, which is its own
  content plus what the person types into it. The Run control there says the
  prototype is not network-contained.
- The import's scan is not a parser. Where it reads a page differently from
  a browser, the design policy's check afterwards refuses the result
  (`unsupported`); it is never drawn under a looser rule.
